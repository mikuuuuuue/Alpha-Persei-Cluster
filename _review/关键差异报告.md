## 六、需要你先决策的 4 件事

**1. 合规策略：`lua_proto_messages.json` 与 `角色挖掘/` 要不要入库？**

你按 NCR-1.0 + README §十 判为「官方衍生数据不入公开仓库」。上游 v5.0.1 已把它们连同 `static_resources/*` 的 321 清单一起提交了。三条路：

- (a) 追随上游入库 —— 简单，但与你自己写下的合规红线冲突；
- (b) 保持 gitignore，只从上游 releases 包取文件 —— 合并需手动 `git rm --cached` 且每次 pull 都要处理；
- (c) 保持 gitignore，但把上游这几个文件 fetch 到本地目录 —— 折中。

**这是唯一挡在 merge 前面的硬决策。**

**2. `res_version_manager.py` 走哪条路？**

- (a) 全取上游（+1109 行，获得动态注册/官方探测/增量下载，但要重验你那套 321 实测值是否都被 THEME_44 覆盖）；
- (b) 保留你的（放弃上游 3 个新功能）；
- (c) 取上游骨架，手工把 321 三平台 hash + 实测注释回填（**推荐**）。

**3. 证书体系留谁的？**

两边各自重造过，二进制互斥。你本地的是真机验证过的；上游的是 v5.0.1 发布包配套的。建议**留本地**，但把上游 `gen_cert.py` 的 `_write_with_backup` + `verify_directly_issued_by` 吸收进来（与你 m2 的 `4fac757` 是同一类修复，可对比取优）。

**4. m2 分支怎么处理？**

`m2` 相对 `origin/main` 是 4 ahead / 45 behind，合并会撞 **15 个冲突**（比 main 多一个 `gen_cert.py`）。建议顺序：**先合并 m2 → main（本地分支，验证通过），再处理上游合并**。否则上游的 `gen_cert.py` 重写会和 m2 的验签/原子写修复搅在一起。
